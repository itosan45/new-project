# 業務自動化ハーネス（開発環境）

設計コンテキスト（`../references/添付資料/業務自動化ハーネス設計コンテキスト.md`）
のうち、画面4種と、その下の骨組みを実装したもの。

このフォルダが、Vercelにデプロイされている実体。以前ここにあった秘書アプリを
置き換えた（Vercel側の Root Directory が `webapp` 固定のため、
フォルダ名はそのまま使っている）。古い秘書アプリは git の履歴に残っている。

## 前提: 人間は1人

この組織に社員はいない。動くのは**自分とAgentだけ**で、判断する人間は自分1人。
これは「今は小さいから」ではなく、設計の前提として扱う。
人が増える前提で作ると、増えるまでずっと使えないものになる。

人が1人しかいないと、こう変わる（`lib/domain/operator.ts`）。

| | 一人のとき |
|---|---|
| 承認 | 全部自分に来る。溜まった時点で全部止まる |
| 担当割り | 無い。Agentか自分かの2択 |
| 限りある資源 | Agentの処理能力ではなく、**自分の時間** |
| 引き継ぎ | できない。記録が残っていることだけが保険 |

そのため上限を数字で持たせてある。

| 上限 | 既定値 | 超えると |
|---|---|---|
| 承認待ち | 5件 | 中身を見ずに押すようになる。そうなったら承認ゲートは無いのと同じ |
| 進行中の案件 | 3件 | 相手の返事待ちは数えない |
| 侵襲度 | L2 まで | L3以上は、復旧できる人間が自分しかいない状態で相手の業務を止める |
| 1日の判断時間 | 240分 | Agentは並列に動くが、判断はここを通る |

役割ごとに分かれた画面（`/employee` `/ceo` `/admin`）は残してあるが、
**いま使うものではない**。社員が入ったとき、あるいはこの仕組みを社員のいる
会社に納めるときに要るもので、入口ページでも分けて置いてある。

**案件は実際に保存される。** `/cases` で受け付けた案件は GitHub
リポジトリの `cases/<tenantId>/<runId>.json` に書き込まれ、承認するたびに
更新される。画面の件数・削減時間は、その実データを数えたもの。

Agentの契約・ドメインパック・仮想顧客は `lib/data/` の定義。
これは設定であってダミーデータではない。

## 起動

```bash
cd webapp
npm install
cp .env.example .env.local   # 値を入れる
npm run dev
```

必要な環境変数:

| 名前 | 用途 |
|---|---|
| `GITHUB_OWNER` / `GITHUB_REPO` / `GITHUB_BRANCH` | 案件の保存先 |
| `GITHUB_TOKEN` | `contents: write` 権限のトークン |
| `APP_PASSWORD` | ログインパスワード |

鍵が未設定でも画面は開く。何が足りないかを画面上で表示する。

## 動作確認

```bash
npm test
```

検証が76件。うち8件が承認ゲートで、**実行系Agentが承認前に完了しないこと**を
確かめている。ここが壊れると、AIが承認なしに外部送信できる状態になるため、
他のどのテストより優先して通っている必要がある。
10件は段階の進行条件（`checkGate()`）で、聞けていないのに提案へ、
承諾されていないのに制作へ、が通らないことを確かめている。
5件は一人で回す前提で、上限の判定と、架空の担当者が混ざっていないこと。
残りはWeb制作Agentの入力不足での停止と、**やっていないことを完了にしない**再発防止。

## 仮想顧客（`/tenants`）

「どの会社でも対応できる」を目指すと、コネクタも承認理由も効果測定も決まらない。
具体的な3社を置いて、そこから逆算している。

| 会社 | 業種 | 最初の1業務 | 承認ゲートが守るもの |
|---|---|---|---|
| 三河ハウスサポート | 住宅リフォーム | 手書き調査票 → 見積書 | **品質**（OCRは必ず読み違える） |
| みらい会計パートナーズ | 税理士法人 | 領収書 → 会計ソフト | **責任**（説明できない出力は使えない） |
| ルミエール | 化粧品D2C | 問い合わせの分類・回答案 | **爆発半径**（1件の誤送信が数万人に届く） |

3社とも承認ゲートを必要とするが、守っているものが違う。
**同じ仕組みを別業種へ横展開できる根拠はここにある。**

各社に3名ずつ、計9名のペルソナを置いている。ペルソナには
`concern`（AIに対する警戒）を必ず持たせてある。ここに答えられない限り
導入されないため、機能一覧より重い情報として扱う。

たとえば三河ハウスサポートの調査員はITリテラシーが低く「スマホで写真を
撮る以上の操作を覚えるつもりはない」。この一行があるだけで、
その画面に入力欄をいくつ置けるかが決まる。

## Agentの専門性（`/agents`）

### 専門性 = 共通Agent × ドメインパック

業種ごとにAgentを作り分けると、**業種 × Agent** の数だけ実装が要る。
建設向けのDocument Readerと会計向けのDocument Readerは同じ実装にして、
読み込む**ドメインパック**だけを変える。

新しい業種の顧客が来たときに追加するのはパック1つで、Agentは触らない。
ここを分けた瞬間に横展開できなくなる。

| パック | 対象業種 | 差し込むAgent |
|---|---|---|
| 建設・リフォーム | 住宅リフォーム、防蟻工事、工務店 | document-reader, validator, data-analyst |
| 士業・会計 | 税理士法人、会計事務所、記帳代行 | document-reader, validator, audit, data-analyst |
| EC・D2C | EC、D2C、通販、サブスク | classifier, draft-writer, voice-of-customer, data-analyst |

パックが持つもの: 分野の語彙、抽出項目とその手がかり、検証ルール、
**必ず人間に回すもの**（業界の慣習や法令に由来する）。

### 契約に「できないこと」を持たせる

`AgentContract` は権限（何をしてよいか）だけでなく、専門性を持つ。

| 項目 | 中身 |
|---|---|
| `expertise` | 具体的に何が得意か |
| `notSuitableFor` | **使ってはいけない場面** |
| `requiredInputs` | 揃わなければ起動させない入力 |
| `produces` | 出力するもの |
| `qualityRisks` | 既知の弱点。隠さず書く |
| `escalatesWhen` | 確信度以外の、人間への引き渡し条件 |
| `maturity` | 動く / 中身あり・未接続 / 契約だけ / 検討中 |
| `experience` | 判断基準・地雷・相場・いまの標準（確認日つき） |

`notSuitableFor` が `expertise` より重要。できることの一覧しか無いと、
「たぶんできるだろう」で守備範囲外の仕事が回ってきて事故る。

`qualityRisks` は正直に書く。たとえば Document Reader には
「手書きの1と7を取り違える」と書いてある。ここを書かないと、
運用側で回避策を用意できない。

### Agentは17体。ただし全社に配らない

追加の基準は「仮想顧客3社のどれかが実際に必要としているか」だけ。
あったら便利そう、では足さない。

- 三河ハウスサポート: 6体（intake, document-reader, validator, approval, executor, audit）
- みらい会計パートナーズ: 6体（+ qa、− executor）
- ルミエール: 8体（classifier, draft-writer, voice-of-customer 中心）

使わないAgentは配らない。権限の穴にしかならないため。

## 型に落とした設計判断

設計書のルールのうち、**守り忘れると事故になるもの**は型と表示に埋め込んである。

1. **承認ゲート**
   `ApprovalRequest.reason` を必須にしてある。理由の書けない承認要求は
   作れない。Approval Agent の `forbiddenActions` には「承認の代行」が
   入っている（自分で通せたら承認ゲートの意味がない）。

2. **「成功」「部分成功」「未実行」を混ぜない**
   `RunStatus` を10種に分け、`RUN_TONE` で色を分けている。
   ここを同色にした瞬間、設計書が目標ゼロに置く
   「未実行を成功扱いした件数」が発生し始める。

3. **バージョン固定**
   `Run.workflowVersion` を Run が持つ。開始時に固定し、途中で最新版に
   差し替えない。差し替えると再現も監査もできなくなる。

4. **二重実行の防止**
   `Run.idempotencyKey` を持ち、ライブ実行トレース画面にも表示している。
   事故調査で最初に必要になる情報のため。

5. **根拠のない結果を出さない**
   `Decision` は `evidence` を必須で持つ。AIアシスタントの回答にも
   参照ソースを必ず添える。

6. **削減効果には算出根拠を添える**
   `SavingMetric.basis` を必須にしてある。設計書には算出方法の定義が
   なかったが、推定値のままROI提案に使うと商談で崩れるため、
   型のレベルで根拠を強制している。画面ではホバーで見える。

7. **会社をまたがせない**
   `TenantScoped` を継承させ、全データに `tenantId` を持たせている。

8. **権限は入口で分ける**
   同じ画面を権限で出し分けず、`/employee` `/ceo` `/admin` と分けている。
   出し分けは隠し忘れが事故に直結する。

## Agentに中身がある／無い（ここが一番大事）

以前このリポジトリは、**何もしていない工程を「完了」と表示していた。**
`pipeline.ts` が承認の要らない工程を無条件で完了にし、契約に書いた
「得意なこと」の1行目を実績として監査ログに書いていた。
`maturity: "実装済み"` が11体に付いていたのも同じ問題の表側。

いまは型と実装の両方で塞いである。

| 工程の状態 | 意味 |
|---|---|
| `COMPLETED` | 実体が動いて、結果が出た |
| `NEEDS_INPUT` | 入力が足りないので実行していない（推測で埋めない） |
| `NOT_IMPLEMENTED` | Agentの中身がまだ無い |
| `WAITING_APPROVAL` | 承認ゲートで停止 |

監査ログの状態にも `未実行` がある。成功でも失敗でもない。
**完了と同じ色にはしない。**同色にした瞬間、やっていないものがやったことになる。

### 契約と実体を分けてある

- 契約 = `lib/data/agents.ts`（何をしてよいか）
- 実体 = `lib/agents/registry.ts`（実際に処理するもの）

レジストリに無いAgentは動かない。`maturity: "動く"` を名乗れるのは
実体があるものだけで、**テストで固定してある**。表示だけ書き換えても通らない。

案件を1件流すと、いまはこうなる。

```
NOT_IMPLEMENTED  intake           受付 Agent はまだ中身がありません（契約のみ）。
NOT_IMPLEMENTED  document-reader  Document Reader はまだ中身がありません（契約のみ）。
NOT_IMPLEMENTED  validator        Validator はまだ中身がありません（契約のみ）。
WAITING_APPROVAL executor         金額変更にあたるため、承認を待っています。
```

承認しても `PARTIAL_SUCCESS` で、成功にはならない。承認＝実行ではないため。

## 依頼はここから出す（`/request`）

**口頭で秘書に頼むと、秘書が全部やってしまい、Agentが1体も動かない。**
実際にそうなっていた（遠州急行のデザイン案を、役割分担Agentを1体も
通さずに手で作った）。Agentを増やしても、通る口が無ければ動かない。

`/request` から出すと、`WEB_HANDOFF` の順で5体が動く。

    ヒアリング設計 → 情報設計 → 工数見積 → 公開前チェック → 計測設計

- **途中で止まっても後ろも動かす**。足りないものをまとめて知りたいので。
  1体目で止めて聞きに行くと、打ち合わせが何回にも増える
- **空欄のまま出してよい**。何が足りないかを返すのがこの画面の仕事
- 結果は `web-requests/<id>.json` に保存される

## 成果物はどこから出てくるか

**以前は出ていなかった。** `Artifact` も `Deliverable` も型があるだけで、
どこからも作られていなかった。書いていたのは `cases/` と `web-requests/` の
記録だけで、実物は秘書が手で作ってエンジンの外に置いていた。

いまは `/request` の最後で **提案書作成 Agent** が動き、
`deliverables/<依頼ID>/提案書_<顧客名>_<日付>.md` に書き出す。

| 前提 | 中身 |
|---|---|
| 前のAgentが止まっていれば作らない | 情報設計と工数の結果が要る |
| 新しい事実は作らない | 前の結果を組み立てるだけ |
| 未確定は埋めない | 「（未確定）」と書き、**顧客に出せない**判定にする |
| 金額は書かない | 作業量と根拠まで。いくらで売るかは人が決める |

### 受け渡しが実際に通るようになった

`WEB_HANDOFF`（受け渡しの順番）は定義してあったのに、**何も渡していなかった**。
5体が独立に動いているだけだった。`AgentContext.prior` を足して、
前の結果を後ろへ積んで渡す。これで「組み立てる」Agentが作れる。

### まだ出ないもの

**HTMLそのものは出ない。** デザインは判断が要るので、決定的な関数にすると
素朴なものしか出てこない。実装Agent（`web-build`）は契約だけのままにしてある。

## 受け取り窓口（`/deliverables`）

作られたものは全部ここに並ぶ。**相手に渡すときは、ここから取り出す。**
保存してあるだけでは受け取れないので、`/api/deliverables/<path>` を通して
ダウンロードする（リポジトリは非公開なので、GitHubの生URLは渡せない）。

### 見た目で判断するものは、画像とPDFで渡す

モック（デザイン案）を **URLやHTMLで渡さない**。

| | 理由 |
|---|---|
| URLで渡さない | 相手が「もう公開されたのか」と迷う。リンクはいずれ切れる |
| HTMLで渡さない | 社内で回覧するときに、開けない人が出る |
| PDF・画像で渡す | そのまま転送でき、印刷して会議に出せる |

PDFは**1枚の長いページ**にする。複数ページに切ると、デザインが途中で
分断されて判断できない（最初4ページに切れていたのを直した）。

ホームページの仕事は、**着工前にモックを出して合意を取ってから**作り始める。
6段階の「提案」の成果物にモックが入っている。

## できること・できないこと（`/can`）

「Agent 25体のうち6体が動く」では、仕事の話が来たときに答えられない。
**このぐらいなら作れる、を数字で出す画面。**

ホームページを3段階（1ページ / 5ページ / しっかり作る）で示し、
期間・作業日数・含むもの・含まないものを並べてある。

**数字はこの画面に書いていない。工数見積Agentにその場で計算させている**
（`lib/data/service-tiers.ts`）。直接書くと、単価表を直したときにずれる。

期間は作業日数と分けてある。「週3日ぶんを充てる＋素材待ち1〜3週」という
前提を画面に書いた。前提なしに週数だけ出すと、その数字で握られる。

出しているのは**時間だけで、金額は出さない**。いくらで売るかは人が決める。

### 使う道具の状態も出す

「Figmaが使えます」と書く前に実際に叩いて確かめる。
繋がっていても権限が足りないことがある（`lib/data/tools.ts`）。

2026-08-19 時点では、Figma は席が「閲覧」で作成・編集ができず、
WordPress.com は機能が未許可、Canva は未認証。
**現実に取れるのは「コードで直接作って Vercel に出す」1本。**

状態は変わるので確認日を持たせてある。日付の無い「使えます」は信用できない。

## Document Reader は ocr-excel に繋いである

`ocr-excel/lib/抽出.py` の抽出規則を TypeScript に移した
（`lib/agents/doc/extract.ts`）。Vercel では Python が動かないため。

**2か所に同じ規則があるので、Python のテストと同じケースを
TypeScript 側にも置いてある。** 片方だけ直すと落ちる。

### OCR そのものは含まない

画像から文字を読むのは前の工程（スキャナ、Googleドライブの読み取り）。
この Agent が受け取るのは**読み取り済みの全文**。`ocr-excel` も同じ前提。

### 「共通Agent × ドメインパック」が実際に動いている

実装は業種を知らない。何をどう探すかは `DomainPack.extractionFields` が持つ
（`kind` = 日付 / 金額 / 電話番号 / キーワード、`clues` = 手がかり）。
元は `ocr-excel/設定.yaml` の同じ仕組み。

同じ領収書を建設パックと会計パックで読ませると、探す項目が変わる。
**Agentは1つのまま。** テストで確認してある。

### 取れなかったら「人に回す」

`NEEDS_REVIEW`（要確認）。入力はあり、出力も出ているが、必須項目が
取れていないので次へ渡せない状態。完了に混ぜると、読み違えたまま見積が作られる。

### 案件受付から書類を渡せる（2026-08-20〜）

前は `documents` を渡す口がどこにも無く、Document Reader は必ず
NEEDS_INPUT で止まっていた（動く実装はあるのに、実際には一度も
動かせない状態だった）。

`/cases` の「案件を受け付ける」に書類欄を足した。受け取るのは
**読み取り済みの全文**だけで、OCRはここに無い。画像・PDFの
文字起こしは別工程のまま。添付できるのは:

- テキストとして直接貼り付け
- `.txt` / `.md` / `.csv` ファイルを選んで読み込み（ブラウザで文字として開けるものだけ）

画像・PDFをそのまま選ばせないのは、選べてしまうと
「読み取ったふり」になるため。`lib/engine/pipeline.test.ts` に、
書類を渡すと実際に COMPLETED になることを確認するテストがある。

### 動かして見つかったバグ

日付の正規表現が4桁を年として拾うため。Python 側にも同じバグがあった。

- 年を 1900〜2100 に限定
- 最初の1件ではなく、条件に合う最初のものを返す

両方の言語を直し、両方にテストを足した。**机上では見つからなかった。**

## Classifier で EC パックを動かす（2026-08-20〜）

EC・D2Cパック（`appliesTo: classifier, draft-writer, voice-of-customer,
data-analyst`）は、実装のあるAgentが1体も差し込まれていなかった。
`extractionFields` は定義されていても、一度も動いたことが無い状態だった
（建設・会計パックは Document Reader が実際に読んでいるのと対照的）。

`classifier`（`lib/agents/ec/classifier.ts`）を実装し、EC・D2Cパックを
実際に動かした。ルミエールの案件は、受付フォームの「内容」に問い合わせ
本文を入れると、Document Reader と同じ仕組み（`項目を取り出す`）で
問い合わせ区分・緊急度などに振り分けられる。

### 「感情の強さ 0〜1」は作らない

EC パックにはもともと「感情の強さ（0〜1、文面の語調から）」という項目が
あった。regexで文面から実数の強さを測るのは、根拠のない数字を作ることに
なる。Classifier契約の `notSuitableFor` にも「クレームかどうかの最終判断
（検知までが担当）」と書いてある。

そこで抽出の種類を1つ増やした：**区分**（`ExtractionKind` に追加）。
あらかじめ決めた区分（例：強い／通常）に、手がかりの言葉があるかどうかで
振り分けるだけで、強さの数値化はしない。`lib/agents/doc/extract.ts` の
`区分を選ぶ` がこれをやる。日付・金額・電話番号・キーワードと違い、
ocr-excel（Python）側には無い、こちら独自の追加。

### Document Reader と同じ実装を共有する

書類を読むDocument Readerと、問い合わせ文を読むClassifierは、
入力の形が違うだけで（複数の書類 vs 1件のテキスト）、項目の探し方は
同じ`項目を取り出す`を共有している。以前はDocument Readerの中に
switch文が1つだけあったが、2つ目のAgentができた時点で
`lib/agents/doc/extract.ts` に出して共有した。ここが2か所に分かれて
別々に直されると、ずれる。

### 確認できたこと

- 配送に関する問い合わせ → 「配送」区分、緊急度は「通常」
- 肌トラブルの訴え → 「品質」区分、緊急度は「最優先」（パックの
  `hint: "肌トラブルの訴えは最優先"` の通りに動く）
- 強い苦情の言葉があれば感情の強さが「強い」、無ければ既定の「通常」
- どの区分の手がかりにも当たらなければ、「その他」と決めつけず
  空欄のまま人に回す

## Web制作（`/web`）

「ホームページを作ってください」は、それ自体では発注になっていない。
決めることが18項目ある（`lib/data/web-decisions.ts`）。
各項目は質問文だけでなく、**なぜ聞くか / 決まらないと何が起きるか /
見積を止めるか / どの回で聞くか**を持つ。

### 業種パックと職種Agentは別の軸

- 業種パック（建設・会計・EC）= 相手の分野の知識 → 共通Agentに差し込む
- 職種Agent（Web制作）= うちの作業の役割分担 → Agentとして足す

建設会社のHP案件 = 職種Agent群 × 建設パック。混同すると、
業種ごとにWeb制作Agentを作ることになる。

### 8体。うち5体は実際に動く

| Agent | 中身 | 止まる条件 |
|---|---|---|
| ヒアリング設計 | **動く** | — |
| 情報設計 | **動く** | 狙い・見る人・してほしい行動のどれかが無い |
| 見積根拠 | **動く** | 作り方・ページ数・動き・文章担当・チャットのどれかが無い |
| 計測設計 | **動く** | **基準値（いまの件数）が無い** |
| 公開前チェック | **動く** | 置き場所・ドメインが無い |
| コピー / ビジュアル / 実装 | 契約だけ | 判断が要るので秘書がやる |

### 「ベテラン」は経歴文ではない

`AgentExperience` として、判断基準・地雷・相場・いまの標準（**確認日つき**）を持つ。
トレンドは黙って腐るので、`isStale()` で期限切れを検出して画面に出す。

参照されない経歴は飾りなので、実際に出力へ効かせてある。
見積の単価は `lib/data/web-rates.ts` が唯一の出どころで、契約に書いてある
相場も同じ数字を見る。**ここを書き換えると見積の出力が変わる。**

## 仕事の流れ（`/flow`）

あなたが仕事を取ってくる。秘書が壁打ちと打ち合わせをして、Agentに作業を投げる。
その一連を6段階に分けてある。定義は `lib/data/stages.ts`、
型と進行条件は `lib/domain/engagement.ts`。

```
相談 → 提案 → 制作 → 納品 → 完了 → 運用
              （途中で終わる道: 見送り / 中止）
```

**段階の切れ目は「相手の返事待ちになる場所」に置いている。**
自分の中だけで進む作業を分けると、動いていないのに段階だけ進む、
という嘘の進捗が生まれるため。

### 相談と提案は1回で終わらない

3〜4回まわるのが普通なので、この2つだけ「1回ぶんの手順」を持たせてある
（`StageDefinition.repeats`）。

| 段階 | 1回の単位 | 次の回に行くか、次の段階に進むかの分かれ目 |
|---|---|---|
| 相談 | 打ち合わせ1回 | `stillUnknown`（まだ分からないこと）が空になったら提案へ |
| 提案 | 提案1版 | 承諾なら制作へ。修正依頼なら指摘を記録して次の版へ |

打ち合わせで一番重要な記録は `stillUnknown`。これが次回の議題になり、
これが空になって初めて提案を書き始める。「なんとなく分かった気がする」で
提案を書くと、後で必ず戻る。

提案は版ごとに `feedback`（相手からの指摘）を残す。残さずに版だけ重ねると、
同じ指摘を二度受ける。

### 提案書は合議でつくる（`proposal-architect`）

顧客の希望をそのまま提案書にすると、できない約束が混ざる。
提案設計Agentが各Agentに意見照会し、返ってきたものを集約して提案書を組み立てる。

| 集めるもの | 提案書のどこになるか |
|---|---|
| `ideas`（こうすればできる） | やること |
| `cannotDo`（うちでは無理） | **やらないこと** |
| `concerns`（ここが危ない） | 前提条件 / 承認ゲートの設計 |
| `feasibility`（できる・条件つき・できない） | 受けるかどうかの判断材料 |

誰の意見かを `agentId` で残す。匿名の箇条書きにすると、後で
「この懸念は誰が言ったのか」を追えなくなり、責任の所在が消える。

`concerns` には答え（`answer`）を書く欄がある。**未回答の懸念が残っている間は
提案を出せない**（`unansweredConcerns()` がゲートで効く）。答えていない懸念は、
制作か納品のどちらかで必ず表に出てくる。

提案設計Agentの `forbiddenActions` には「金額の確定」「懸念の削除」が入っている。
集約役が金額まで決められると、誰も止められなくなる。

### どこまで踏み込むか（侵襲度 L0〜L4）

相談の段階でここを決めないと、提案が書けない。

| 段 | どこまで | 例 |
|---|---|---|
| L0 | 触らない | SNS運用、コンテンツ制作 |
| L1 | 読むだけ | Drive・Dropboxから読んで集計 |
| L2 | ファイルに書く | Excelへの転記 |
| L3 | 業務システムに書く | CRM・会計ソフトへの登録 |
| L4 | 業務フローを置き換える | 受発注プロセスの刷新 |

低いほど売りやすく、事故っても影響が小さい。高いほど単価が上がるが信頼が要る。
**下から順に上がっていくもので、いきなり上は受けない。**

### 段階を進める条件はコードにある

`checkGate()` が、その案件のデータを見て「次へ進めるか」を返す。
画面に書いた説明文ではなく、この関数の結果を表示している。説明と実装が
ずれないようにするため。検証は `lib/domain/engagement.test.ts` に10件。

## 案件の流れ（`/cases`）

```
案件を受け付ける
  ↓
tenant.requiredAgents の順にAgentが動く
  ↓
副作用のあるAgent（SIDE_EFFECT / IRREVERSIBLE）の手前で必ず停止
  ↓  status = HUMAN_REVIEW（成功ではない）
人が承認 or 差し戻し
  ↓
承認 → 残りを実行して SUCCEEDED
差し戻し → SKIPPED を残して BLOCKED（失敗ではなく未実行）
```

止める判断は `AgentContract.sideEffectClass` から自動で決まる。
画面や案件ごとに書かない。書くと必ず書き忘れる。

`lib/engine/pipeline.ts` が実行しているのは
**順序・停止条件・記録の3つだけ**で、Agentの中身の処理はまだ行っていない。
これは手抜きではなく順序の問題で、中身の精度は後から差し替えられるが、
承認せずに送ってしまった・記録が無いから説明できない、は後から直せない。
中身を本物にするときは `runStep()` の中だけを差し替える。
