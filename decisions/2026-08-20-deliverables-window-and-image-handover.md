## きっかけ

「成果物の受け取り窓口がハーネスのどこになるのか、そこもはっきりさせるべき」
「ホームページみたいなビジュアルで判断するものは、一旦HTMLやURLで渡さずに、
デザインが決まった時点で画像ファイルで出力して顧客に渡す。PNG・PDF・JPEG は
どうだろうか」
「ホームページのモックみたいなものを最初に作ってから着工する形なので、
成果物としてモックを提出する過程は当然必要」

## 決めたこと1: 受け取り窓口は `/deliverables`

作られたものは全部ここに並ぶ。相手に渡すときはここから取り出す。

保存してあるだけでは受け取れない。`/api/deliverables/<path>` を通して
ダウンロードする。リポジトリは非公開なので、GitHubの生URLは相手に渡せない。

画像はその場で表示する。送る前に中身を確認できないと、窓口の意味がない。

## 決めたこと2: 見た目で判断するものは、画像とPDFで渡す

**URLやHTMLでは渡さない。**

| | 理由 |
|---|---|
| URL | 相手が「これはもう公開されたのか」と迷う。リンクはいずれ切れる |
| HTML | 社内で回覧するときに、開けない人が出る |
| PDF・画像 | そのまま転送でき、印刷して会議に出せる |

### PDFは1枚の長いページにする

最初に出したPDFは**4ページに切れていた**。デザイン案が途中で分断されると、
見た目の判断ができない。ページ高さを本文の高さに合わせて1枚にした。

### 大きさ

PC版のPNGが5.5MBあった。送れないので、幅を落としてJPEGにした。

| ファイル | 大きさ |
|---|---|
| PDF（1枚） | 1.9MB |
| PC版 JPEG（1440px幅） | 675KB |
| スマホ版 JPEG（600px幅） | 737KB |

スマホ版は縦19,000pxあり、そのままでは見るのがつらいので幅を落とした。

## 決めたこと3: モックは提案の成果物

6段階の「提案」の成果物に**モック（デザイン案）**を加えた。
着工前にモックで合意を取ってから作り始める。

「提案」の1回分の手順にも
**「モックを画像とPDFに書き出す。URLやHTMLでは渡さない」**を入れた。

落とし穴にも足した:
**見た目の話をモック無しで言葉だけで進めると、ここで必ず食い違う。**

## 型に足したもの

- `DeliverableKind`（提案書 / モック / 議事録 / 見積 / その他）
- `DeliverableFormat`（md / pdf / png / jpg / html）
- `isSendable()` — そのまま顧客に送れる形式かどうか
- `putBinaryFile` / `getBinaryFile` — 画像とPDFを扱う口。
  既存の `putFile` はUTF-8として読むので、画像を通すと壊れる

## まだ手作業なところ

**書き出し（HTML → 画像・PDF）は、ブラウザのある場所でしか動かない。**
Vercel の実行環境にはブラウザが無いので、いまは私の側で書き出して
リポジトリに置いている。ここを自動にするなら、書き出し専用の場所が要る。
