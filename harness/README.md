# 業務自動化ハーネス（開発環境）

設計コンテキスト（`../references/添付資料/業務自動化ハーネス設計コンテキスト.md`）
のうち、画面4種と、その下の骨組みを実装したもの。

現時点ではデータは `lib/data/` の固定値。DBもAPIもまだ繋いでいない。
ただし**画面が読む型は本番と同じ**にしてあるので、データ供給元を差し替えれば
画面側は変えずに動く。

## 起動

```bash
cd harness
npm install
npm run dev
```

http://localhost:3000 を開くと画面一覧が出る。

## 画面

| URL | 画面 | 役割 |
|---|---|---|
| `/` | 画面一覧 | 開発用の入口。Agent契約の一覧も出る |
| `/employee` | お仕事コックピット | 社員 |
| `/ceo` | CEOアシスタント | 経営 |
| `/admin` | エージェント運用センター | 管理者 |
| `/admin/live` | ライブ実行トレース | 管理者 |

ナビには設計書にある画面名を先に全部並べてある。未実装のものを踏むと
「まだ作っていません」と出る（素の404にはしない）。

## 骨組み

### `lib/domain/types.ts`

画面はここで定義した型だけを読む。UIに都合のよい別の形を作らないこと。
作った瞬間に、画面と実体がずれ始める。

| 型 | 役割 |
|---|---|
| `Run` / `RunStep` | 1件の処理と、その中の各ステップ |
| `AgentContract` | 何をしてよく、何が禁止かの契約 |
| `AgentRuntimeState` | 稼働状況（契約とは分ける） |
| `ApprovalRequest` | なぜ人間の承認が要るかを持つ承認要求 |
| `Artifact` | 成果物と、その元になった成果物の系譜 |
| `AuditEvent` | 誰が・いつ・何をしたかの記録 |
| `SavingMetric` | 削減効果と、**その算出根拠** |

### `lib/data/`

| ファイル | 中身 |
|---|---|
| `agents.ts` | Agent契約8体と、その稼働状況 |
| `runs.ts` | ライブ実行トレースが表示している Run と実行ログ |
| `workspace.ts` | 社員・CEO・管理者の各画面が使うデータ |

### `components/`

| ファイル | 中身 |
|---|---|
| `ui.tsx` | Card / Badge / Button / Metric / 進捗 / 簡易チャート / アイコン |
| `shell.tsx` | 役割別のサイドバー付き外枠 |
| `admin-nav.tsx` | 管理者側の共通ナビ |

チャートとアイコンは外部ライブラリを入れずSVGで自前実装している。
依存を増やすほど、後から動かしにくくなるため。

## 型に落とした設計判断

設計書のルールのうち、**守り忘れると事故になるもの**は型と表示に埋め込んである。

1. **承認ゲート**
   `ApprovalRequest.reason` を必須にしてある。理由の書けない承認要求は
   作れない。Approval Agent の `forbiddenActions` には「承認の代行」が
   入っている（自分で通せたら承認ゲートの意味がない）。

2. **「成功」「部分成功」「未実行」を混ぜない**
   `RunStatus` を10種に分け、`RUN_TONE` で色を分けている。
   ここを同色にした瞬間、設計書が目標ゼロに置く
   「未実行を成功扱いした件数」が発生し始める。

3. **バージョン固定**
   `Run.workflowVersion` を Run が持つ。開始時に固定し、途中で最新版に
   差し替えない。差し替えると再現も監査もできなくなる。

4. **二重実行の防止**
   `Run.idempotencyKey` を持ち、ライブ実行トレース画面にも表示している。
   事故調査で最初に必要になる情報のため。

5. **根拠のない結果を出さない**
   `Decision` は `evidence` を必須で持つ。AIアシスタントの回答にも
   参照ソースを必ず添える。

6. **削減効果には算出根拠を添える**
   `SavingMetric.basis` を必須にしてある。設計書には算出方法の定義が
   なかったが、推定値のままROI提案に使うと商談で崩れるため、
   型のレベルで根拠を強制している。画面ではホバーで見える。

7. **会社をまたがせない**
   `TenantScoped` を継承させ、全データに `tenantId` を持たせている。

8. **権限は入口で分ける**
   同じ画面を権限で出し分けず、`/employee` `/ceo` `/admin` と分けている。
   出し分けは隠し忘れが事故に直結する。

## 次にやること

1. 固定データを DB（PostgreSQL）に移す
2. 指示登録・承認操作を実際に保存する
3. 承認による Run の再開を動かす
4. 1つの実システム（メールまたはCRM）と繋ぐ

なお、設計書は16 Agent・3プレーン構成を前提にしているが、初期に全部
立ち上げると担当が重なって追跡できなくなる。ここでは重複の少ない8体から
始めている。増やすときは `lib/data/agents.ts` に足す。
