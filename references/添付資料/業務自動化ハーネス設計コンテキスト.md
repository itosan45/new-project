# 業務自動化ハーネス 設計コンテキスト

## 1. 構想

どの会社でも一定範囲の業務自動化に対応できる、企業向けの「業務自動化ハーネス」を構築する。

単体のAIエージェントではなく、共通の実行エンジン、会社別コネクタ、会社別設定、承認・監査・復旧機能を組み合わせる。

### 基本思想

> 共通の実行エンジン + 会社別コネクタ + 会社別設定 + 承認・監査・復旧

送信、削除、金額変更、契約などの重要操作は、AIだけで確定させず、人間の承認ゲートを標準装備する。

## 2. 収益ループ

```text
無料診断
  ↓
業務の詰まりを可視化
  ↓
小さな自動化を有料導入
  ↓
削減時間・売上増・ミス削減を測定
  ↓
別部署・別業務へ横展開
  ↓
月額利用料 + 追加自動化費
  ↓
運用データから次の改善提案
  ↺
```

### 収益モデル

1. 初期診断・設計費
2. 導入・システム連携設定費
3. 月額ハーネス利用料
4. エージェント稼働料
5. 追加コネクタ・追加業務料金
6. 運用保守・改善契約
7. 成果報酬または削減額連動

「何でもできます」と売るのではなく、1業務で成果を出し、その成果を根拠に別部署へ展開する。

## 3. エージェントの担当仕分け

| Agent | 担当 | 主な成果物 |
|---|---|---|
| Intake Agent | 依頼受付、目的・期限・対象の整理 | 構造化された依頼 |
| Discovery Agent | 現場業務、利用システム、例外の調査 | 業務課題・例外一覧 |
| Process Agent | 業務フロー分解、自動化候補作成 | ワークフロー案 |
| Marketing Research Agent | 市場、競合、顧客ニーズ、業界動向の調査 | 市場仮説、競合比較 |
| Voice of Customer Agent | 問い合わせ、メール、レビュー、商談記録の分析 | 顧客課題、離脱理由 |
| Data Analyst Agent | 売上、時間、CVR、対応件数の分析 | KPI、傾向、異常、優先度 |
| Revenue Analyst Agent | 自動化効果、利益、ROI、回収期間の計算 | ROI・追加提案候補 |
| Connector Agent | Gmail、Teams、CRM、会計などとの接続 | 接続・同期設定 |
| Builder Agent | ワークフロー、スクリプト、AI処理の構築 | 実行可能な自動化 |
| Decision Agent | ルール・データに基づく判断 | 処理方針・判断根拠 |
| Approval Agent | 人間承認が必要な案件の停止・依頼 | 承認タスク |
| Executor Agent | 承認済みの送信、登録、更新 | 実行結果 |
| QA Agent | 件数、金額、宛先、漏れ、出力の検査 | 検査結果 |
| Recovery Agent | 失敗時の再試行、復旧、途中再開 | 復旧結果 |
| Audit Agent | 操作履歴、根拠、承認者の記録 | 監査ログ |
| Growth Agent | 次に狙う顧客、部署、商品、業務の提案 | 拡張候補 |

### 管理原則

エージェント同士を自由に接続せず、中央のOrchestratorが担当と順序を管理する。

- 調査系：読む、整理する、提案する
- 実行系：登録、送信、更新する
- 管理系：承認、監査、復旧する
- 収益系：効果測定、請求、横展開する

## 4. 1体のエージェントとの違い

1体の汎用Agentは導入が速く安価だが、複数システム・例外処理・監査・権限管理で文脈が混線しやすい。

ハーネス型は初期構築が重い一方、担当分離により、同時処理、障害局所化、監査、他部署展開、継続課金に向く。

### 設計上の試算（実測値ではない）

| 指標 | 1体のAgent | ハーネス型 |
|---|---:|---:|
| 自動化率 | 40〜60% | 70〜90% |
| 対応業務 | 1〜3種類 | 5〜20種類 |
| 失敗時の復旧 | 手動確認中心 | 再試行・途中再開 |
| 展開範囲 | 1部署中心 | 複数部署・全社 |

## 5. クラウド上の共有コンテキスト

エージェントごとにデータを持たせず、クラウド上の「共有コンテキスト基盤」を正本にする。

```text
各社データ
  ↓
収集・同期
  ↓
クラウド・コンテキスト基盤
  ├─ 業務データDB
  ├─ 文書・画像ストレージ
  ├─ ベクトル検索
  ├─ イベント履歴
  ├─ KPI・分析データ
  └─ 権限・監査ログ
  ↓
Context Gateway
  ↓
各エージェント
```

### データの保存先

| データ | 保存先候補 |
|---|---|
| 顧客、案件、売上、タスク | PostgreSQL |
| PDF、メール添付、画像 | S3互換オブジェクトストレージ |
| 文書検索用インデックス | pgvectorまたは専用ベクトルDB |
| 実行履歴・判断履歴 | Event Log |
| 集計・KPI | Analytics Warehouse |
| 会社別設定 | Tenant Configuration DB |
| 秘密情報 | Secrets Manager |

AgentはDBを直接操作せず、Context Gateway経由で必要な範囲だけ取得する。

### 必須メタデータ

```text
tenant_id
workspace_id
user_id
role
data_classification
source
observed_at
expires_at
```

会社間のデータ混入を防ぐため、全データにtenant_idを付ける。個人情報、財務、社外秘、公開情報などの分類と、Agentごとの閲覧権限を設ける。

## 6. システムアーキテクチャ

```text
[管理画面 / 社員画面 / CEO画面]
          ↓
[Control API]
          ↓
[Orchestrator]
          ↓
[Agent Runtime]
  調査 / 分析 / 実行 / QA / 承認Agent
          ↓
[Context Gateway]
          ↓
[PostgreSQL / Object Storage / Vector Search]
```

### 推奨技術スタック

| 領域 | 推奨 |
|---|---|
| Web UI | Next.js、TypeScript |
| UI | Tailwind CSS、shadcn/ui |
| API | FastAPIまたはNestJS |
| 非同期ワークフロー | Temporalまたはジョブ基盤 |
| キュー | Redisまたはクラウドキュー |
| DB | PostgreSQL |
| ベクトル検索 | pgvector |
| ファイル | S3互換ストレージ |
| 認証 | Auth0、Keycloak、Entra ID等 |
| リアルタイム | SSE、必要に応じてWebSocket |
| 監視 | OpenTelemetry、Sentry |
| 配布 | Docker。Kubernetesは規模拡大後 |

### 3つのプレーン

- Control Plane：設定、権限、承認、監査
- Agent Runtime：AI処理と業務ワークフロー
- Context Layer：会社データへの安全なアクセス
- Execution Layer：メール送信、CRM更新、ファイル生成

## 11. 重要な設計ルール

- AIにすべてを記憶させず、クラウドを正本にする
- 必要なデータだけをContext Gatewayから取得する
- 会社ごとにtenant_idで完全分離する
- 送信・削除・金額変更・契約は承認必須にする
- プロンプトや権限は下書き → テスト → 承認 → 公開で変更する
- 成功、部分成功、未実行を分けて表示する
- 実行結果だけでなく、判断理由・出典・取得時刻を保存する
- エージェントの失敗を局所化し、再試行と途中再開を可能にする

## 14. バグ監視・自動復旧ループ

システムが壊れた場合に、ただ再実行するのではなく、原因を分類し、安全な範囲で復旧してから検証する。

```text
メトリクス・ログ・実行結果を収集
  ↓
異常検知
  ↓
影響範囲を特定
  ↓
原因を分類
  ↓
安全な自動復旧
  ↓
限定的に再実行
  ↓
結果を独立検証
  ├─ 成功 → 通常運転へ
  ├─ 部分成功 → 未完了だけを保留・通知
  └─ 失敗 → 停止・人間へエスカレーション
```

### 監視対象

- Agentの稼働状態、ハートビート、処理時間
- 成功率、失敗率、タイムアウト、再試行回数
- 入力件数と出力件数の差
- APIのレート制限、認証エラー、接続エラー
- 重複実行、二重送信、データ欠損
- AI出力の形式違反、信頼度低下、根拠不足
- クラウドストレージ、DB、キューの容量と遅延
- コスト急増、異常なトークン使用量

### 障害の分類と復旧策

| 障害分類 | 自動復旧 | 人間対応 |
|---|---|---|
| 一時的なネットワークエラー | 指数バックオフで再試行 | 一定回数超過時に通知 |
| APIレート制限 | 待機、キュー再投入 | 継続時に通知 |
| Agentタイムアウト | 同じ処理を1回だけ再実行 | 再発時に停止 |
| キュー停止 | ワーカー再起動、未処理ジョブ確認 | 復旧不能時に通知 |
| 形式エラー | 出力を検査し、修正Agentへ戻す | 修正不能時に保留 |
| データ同期遅延 | 同期を再実行し、取得時刻を更新 | 最新化不能時に停止 |
| 二重実行の疑い | idempotency keyでブロック | 影響確認後に判断 |
| OAuth・認証切れ | 自動送信せず停止 | ユーザー本人が再認証 |
| 権限不足 | 実行せず停止 | 管理者が権限を確認 |
| データ破損・欠損 | バックアップから読み取り復元 | 書き戻しは承認必須 |
| 外部サービス仕様変更 | コネクタを隔離 | 修正・再テスト後に再開 |

認証、権限、契約、削除、外部送信、金額変更は自動で突破・迂回しない。未実行を成功扱いにせず、`未実行`または`要再認証`として記録する。

### 復旧レベル

#### Level 0：観測

ログ、メトリクス、トレース、入力、出力、エラーを保存する。ここではシステム状態を変更しない。

#### Level 1：安全な再試行

一時的な通信エラーやタイムアウトだけを対象に、指数バックオフ、最大試行回数、重複防止キー付きで再実行する。

#### Level 2：コンポーネント復旧

停止したワーカー、キュー、同期処理を再起動する。再起動前に未処理ジョブと二重実行リスクを確認する。

#### Level 3：処理の隔離・縮退運転

壊れたコネクタやAgentだけを停止し、他の処理を継続する。代替処理は読み取り専用または下書き生成に制限する。

#### Level 4：人間へのエスカレーション

復旧不能、原因不明、機密情報、認証、権限、外部送信、データ破損を含む場合は自動停止し、人間に通知する。

### 復旧コントローラー

```text
Health Monitor
  ↓ 異常イベント
Incident Classifier
  ↓ 障害分類・影響範囲
Recovery Controller
  ├─ Retry Manager
  ├─ Worker Restart
  ├─ Queue Reconciler
  ├─ Connector Circuit Breaker
  └─ Rollback / Snapshot Manager
  ↓
Verification Agent
  ↓
Audit Agent + 通知
```

### 復旧後の検証条件

自動復旧は、次の条件を満たすまで成功と表示しない。

- 入力件数と処理済み件数が一致している
- 重複処理がない
- 出力の必須項目が埋まっている
- 重要な金額・宛先・会社識別子が一致している
- 外部送信が実際に完了している、または未送信として明示されている
- Contextの取得時刻と出典が保存されている
- 再実行前後の差分が監査ログに残っている

### 状態モデル

```text
QUEUED
  → RUNNING
  → RETRYING
  → RECOVERING
  → VERIFYING
  → SUCCEEDED

RUNNING / RECOVERING / VERIFYING
  → PARTIAL_SUCCESS
  → BLOCKED
  → FAILED
  → HUMAN_REVIEW
```

UIでは、`成功`、`部分成功`、`復旧中`、`要確認`、`未実行`、`失敗`を明確に分ける。

### 自動停止条件

- 同じエラーが3回以上連続する
- 再試行によって副作用が発生する可能性がある
- 二重送信・二重登録の可能性がある
- 認証・権限エラーが発生した
- 入出力件数、金額、宛先が一致しない
- 機密データの共有範囲が不明確
- AIの信頼度が設定値を下回る
- コストまたは処理量が異常閾値を超える

### 復旧・障害画面

管理者向けに「障害・復旧センター」を追加する。

- 現在の障害一覧
- 影響を受けた会社、Agent、ワークフロー
- 障害原因の分類
- 自動復旧の実行履歴
- 次の再試行予定
- 部分成功した件数
- 未実行・要確認の件数
- 一時停止・再開・手動再実行
- 復旧後の検証結果
- 監査ログと通知履歴

### MVPで実装する自己修復

最初は次の4つに限定する。

1. タイムアウトの安全な再試行
2. キュー・ワーカーのヘルスチェックと再起動
3. 重複防止キーによる二重実行防止
4. 復旧後の件数・出力・送信状態の検証

OAuth、権限、データ破損、外部送信、削除は自動復旧の対象外にし、必ず人間へ引き継ぐ。

### 成果指標

- 平均検知時間（MTTD）
- 平均復旧時間（MTTR）
- 自動復旧成功率
- 復旧後の再発率
- 部分成功率
- 人間エスカレーション率
- 二重実行件数
- 未実行を成功扱いした件数（目標ゼロ）

## 15. Agent作業データ・ログ・成果物の保存設計

各Agentが個別にファイルを保存すると、途中生成物、最終成果物、根拠資料、ログが混ざり、後から「何が正しい成果物か」「どのデータから作られたか」が分からなくなる。

そのため、Agentは任意の共有フォルダへ直接書き込まず、`Artifact Service`と`Log Service`を通して保存する。

```text
Agent Runtime
  ↓ 保存要求
Artifact Service / Log Service
  ├─ メタデータ台帳（PostgreSQL）
  ├─ 成果物ストレージ（Object Storage）
  ├─ 実行ログ（Event Store）
  └─ 検索インデックス（全文 / Vector）
```

### 保存単位

最上位の単位は会社の`tenant_id`、次に業務領域、案件、実行単位を置く。

```text
tenant_id/
  workspace_id/
    domain/
      case_id/
        run_id/
          00_input/
          10_raw/
          20_working/
          30_evidence/
          40_output/
          50_review/
          60_export/
          90_quarantine/
          logs/
```

### フォルダの意味

| 領域 | 内容 | 扱い |
|---|---|---|
| `00_input` | 依頼文、入力ファイル、実行条件 | 原本。変更不可 |
| `10_raw` | API・メール・CRMから取得した原データ | 原本。取得時刻を保持 |
| `20_working` | Agentの途中ファイル、作業用JSON、抽出結果 | 一定期間後に削除可能 |
| `30_evidence` | 判断根拠、引用箇所、参照元、計算根拠 | 監査用。保持期間長め |
| `40_output` | Agentが作った正式成果物 | バージョン管理 |
| `50_review` | 人間確認中の下書き、差し戻し版 | 承認前。外部共有不可 |
| `60_export` | 承認済みの送信・納品用ファイル | 送信履歴と紐付け |
| `90_quarantine` | 形式不正、ウイルス疑い、検証失敗ファイル | 隔離。通常検索から除外 |
| `logs` | 実行ログ、判断ログ、エラーログ | 追記専用 |

### Agent別の整理

Agent別にトップフォルダを乱立させず、Runの中で`agent_id`をメタデータとして管理する。

```text
40_output/
  artifact_id=art_001__agent=marketing-research__type=report__v=001.pdf
  artifact_id=art_002__agent=data-analyst__type=summary__v=001.xlsx
  artifact_id=art_003__agent=qa__type=validation__v=001.json
```

これにより、同じ案件を複数Agentが処理しても、実行単位、作成者Agent、成果物種別、バージョンを追跡できる。

### 成果物台帳

ファイル名だけを正本にせず、PostgreSQLに成果物台帳を持つ。

```text
artifact_id
tenant_id
workspace_id
case_id
run_id
agent_id
artifact_type
storage_key
version
status
source_artifact_ids
content_hash
mime_type
created_at
created_by
review_status
approved_by
retention_until
```

### 成果物の状態

```text
CREATED
  → VALIDATING
  → DRAFT
  → REVIEW_REQUIRED
  → APPROVED
  → EXPORTED
  → ARCHIVED

CREATED / VALIDATING
  → INVALID
  → QUARANTINED
  → SUPERSEDED
```

Agentが生成したファイルは最初から正式成果物にせず、`DRAFT`または`REVIEW_REQUIRED`にする。承認されたものだけを`60_export`へコピーまたは参照する。

### ログの分離

ログは目的別に分ける。

| ログ | 記録内容 |
|---|---|
| Execution Log | 開始、終了、処理件数、状態遷移 |
| Agent Log | Agentの入力、処理、出力、使用ツール |
| Decision Log | 判断、根拠、信頼度、参照データ |
| Data Access Log | 誰がどのデータを読んだか |
| Artifact Log | 作成、更新、承認、差し戻し、輸出 |
| Error / Recovery Log | エラー、原因分類、再試行、復旧結果 |
| Human Action Log | 人間の承認、修正、送信、削除 |

全ログに最低限、`tenant_id`、`run_id`、`agent_id`、`event_id`、`timestamp`、`actor`、`status`を付ける。

### 関連ファイルの追跡

成果物同士をファイル名で関連付けず、`source_artifact_ids`と`parent_run_id`でつなぐ。

```text
売上_2026Q2.csv
  ↓
Data Analystの集計JSON
  ↓
QA Agentの検証結果
  ↓
マーケティングレポート.pdf
  ↓
CEO承認済み_export.pdf
```

管理画面では、各成果物から「入力原本」「参照根拠」「派生成果物」「承認履歴」を辿れるようにする。

### ファイル保存ルール

- Agentの直接保存先を禁止し、Artifact Serviceだけが保存する
- 原本は上書きしない
- 途中ファイルと正式成果物を同じ場所に置かない
- 承認前ファイルを外部送信領域へ置かない
- 同じ内容はcontent_hashで重複検知する
- ファイル名に個人情報や秘密情報を直接含めない
- `tenant_id`をまたぐコピーを禁止する
- 削除ではなく、原則としてアーカイブまたは隔離する
- 保持期限と削除・匿名化ルールを台帳に記録する

### Agentの作業領域

各Agentには一時的なサンドボックスを割り当てる。

```text
/sandbox/{tenant_id}/{run_id}/{agent_id}/
```

サンドボックス内のファイルは、Agentの処理完了後に自動スキャンする。

- 成果物として登録する
- 根拠資料として保存する
- 破棄する
- 検証失敗として隔離する

未登録のファイルを正式な共有コンテキストに残さない。

### 保存場所の実装候補

| 用途 | 実装候補 |
|---|---|
| 台帳・権限・状態 | PostgreSQL |
| 大容量成果物 | S3、Azure Blob、Google Cloud Storage等 |
| 検索 | PostgreSQL全文検索、OpenSearch、pgvector |
| 追記専用イベント | Event StoreまたはPostgreSQLパーティション |
| 一時作業領域 | Agent専用コンテナの一時ボリューム |
| マルウェア・形式検査 | Upload Scan Worker |

### 管理画面への追加

管理者向けに「データ・成果物センター」を追加する。

- 会社、案件、Run、Agentで絞り込み
- 原本、途中ファイル、根拠、成果物、承認版の分類表示
- 成果物のバージョン比較
- 入力から出力までの系譜表示
- 参照権限とアクセス履歴
- 検証失敗・隔離ファイル
- 保持期限とアーカイブ状態
- ダウンロード・共有・外部送信の監査履歴

社員画面では、自分に権限のある`40_output`、`50_review`、`60_export`だけを表示する。`00_input`や`10_raw`の個人情報・機密データは、権限がなければ存在自体を見せない。

### MVPで作る保存機能

1. `tenant_id / case_id / run_id`の階層
2. `input / working / evidence / output / review / export`の分離
3. 成果物台帳とバージョン管理
4. Agent、Run、元データ、派生成果物の紐付け
5. 実行・判断・アクセス・承認ログ
6. 成果物の検証と隔離

## 16. 権限・承認ポリシー仕様

会社・部門・ユーザー・Agent・Workflow・データ分類・操作種別を分けて権限管理する。`tenant_id`だけを確認して実行を許可してはいけない。

```text
User / Agent
  ↓
Identity + Role + Department + Scope
  ↓
Policy Engine
  ↓
Read / Draft / Approve / Execute / Export / Delete
```

### 操作レベル

| 操作 | 例 | 初期ポリシー |
|---|---|---|
| READ | データ閲覧、検索 | データ分類と所属範囲を確認 |
| DRAFT | 下書き、集計、レポート生成 | Agentに許可可能 |
| REVIEW | 検証、差し戻し | 担当者またはQA |
| APPROVE | 外部送信、金額変更、公開 | 指定承認者 |
| EXECUTE | 送信、登録、更新 | 承認済みのExecutorのみ |
| EXPORT | ダウンロード、社外共有 | 宛先・期限・機密レベルを確認 |
| DELETE | 削除、匿名化 | 原則二人承認または管理者 |

### 承認の無効化条件

承認後に次のいずれかが変わったら、承認を無効にして再承認する。

- 宛先
- 金額
- 本文
- 添付ファイル
- 参照データ
- 機密レベル
- 実行期限
- 実行するWorkflowまたはAgentのバージョン

### 職務分離

作成者が自分の作成物を単独で承認できないようにする。CEO秘書、経理、営業、システム管理者など、業務ごとの承認者と代理承認者を定義する。

## 17. Workflow / Agent実行契約

Agentは自由なチャット参加者ではなく、入力・出力・権限・副作用を定義した実行コンポーネントとする。

### Agent契約

```text
agent_id
agent_version
purpose
input_schema
output_schema
allowed_tools
allowed_data_scopes
allowed_actions
forbidden_actions
timeout
retry_policy
confidence_threshold
validator_id
owner
```

### Workflow契約

```text
workflow_id
workflow_version
trigger
input_schema
steps
approval_points
side_effects
idempotency_strategy
compensation_strategy
success_criteria
failure_policy
retention_policy
```

Workflowはバージョンを固定して実行する。途中で最新プロンプトや最新ルールに置き換えず、Run開始時のバージョンを最後まで保持する。

### 副作用の分類

| 種別 | 例 | 再実行ルール |
|---|---|---|
| READ_ONLY | 検索、集計、取得 | 再実行可能 |
| DRAFT_ONLY | 下書き、レポート生成 | バージョンを分けて再生成 |
| REVERSIBLE | タスク更新、タグ付け | 取消・補償処理を用意 |
| SIDE_EFFECT | メール送信、CRM更新 | 状態照会後のみ再実行 |
| IRREVERSIBLE | 削除、契約、決済 | 人間承認と二重検証が必須 |

### API・実行の必須条件

- すべてのRunに`run_id`と`idempotency_key`を付ける
- 外部APIの呼び出しには`request_id`を付ける
- 途中状態を保存して再開可能にする
- 失敗したStepと成功したStepを区別する
- 同じ入力での再実行結果を記録する
- 副作用の前に最終ポリシー判定を行う
- 予期しないツール呼び出しを拒否する

## 18. データ分類・保持・削除仕様

### データ分類

```text
PUBLIC
INTERNAL
CONFIDENTIAL
PERSONAL
FINANCIAL
SECRET
```

分類ごとに、閲覧Agent、保存場所、暗号化、保持期間、外部API送信可否を定義する。

### 保持と削除

- 原本、根拠、成果物、ログごとに保持期間を設定する
- 会社の退会時は本番、バックアップ、検索インデックス、ベクトルインデックスを削除対象にする
- 法的保全中のデータは削除せず、Legal Holdとして記録する
- 削除・匿名化は実行結果と対象範囲を監査ログに残す
- モデル学習への二次利用は明示的に禁止または同意単位で管理する
- 外部APIへのデータ送信は宛先、項目、時刻、目的を記録する

### バックアップと事業継続

```text
RPO：どの時点まで復旧できれば許容するか
RTO：何時間以内に復旧するか
```

バックアップは取得するだけでなく、定期的にリストアテストを行う。復旧テストの結果をEvidenceとして保存する。

## 19. 障害対応RunbookとSLO

### 重大度

| 重大度 | 例 | 対応 |
|---|---|---|
| P0 | 会社間データ混入、顧客への誤送信、重大な情報漏えい | 即時停止・責任者通知・封じ込め |
| P1 | 重要業務停止、二重送信の疑い | 自動停止・担当者を即時招集 |
| P2 | 一部Agent停止、遅延、部分成功 | 自動復旧・期限内に確認 |
| P3 | 軽微な形式エラー、表示不具合 | 次回リリースで修正 |

### 障害時の手順

```text
検知
  ↓
重大度判定
  ↓
影響範囲の凍結
  ↓
外部副作用の停止
  ↓
証拠保全
  ↓
復旧またはロールバック
  ↓
検証
  ↓
再開判断
  ↓
ポストモーテム
```

### SLOの例

- 重要Workflowの成功率
- 承認待ちの期限内処理率
- 外部送信の重複件数：ゼロ
- 未実行を成功扱いした件数：ゼロ
- P0の検知時間
- P1の復旧時間
- データ混入件数：ゼロ
- 監査ログ欠落件数：ゼロ

SLOを満たさない場合は、新機能追加よりも原因修正を優先する。

## 20. テスト・検証・評価・提出ループ

AgentやWorkflowは、作成してすぐ提出・公開しない。入力、処理、出力、権限、副作用、復旧を段階的に確認する。

```text
要件・受入条件を定義
  ↓
実装・設定
  ↓
単体テスト
  ↓
契約テスト
  ↓
統合テスト
  ↓
E2Eテスト
  ↓
安全性・権限テスト
  ↓
評価データで品質評価
  ↓
人間レビュー
  ↓
提出候補を凍結
  ↓
承認
  ↓
提出・公開
  ↓
本番監視
  ↓
フィードバックを次の評価データへ
  ↺
```

### テストの種類

| 段階 | 確認すること |
|---|---|
| 単体テスト | パーサ、ルール、計算、状態遷移 |
| 契約テスト | Agent間の入力・出力スキーマ |
| 統合テスト | DB、ストレージ、キュー、外部API |
| E2Eテスト | 依頼から成果物、承認、送信まで |
| 権限テスト | 会社・部門・役職・Agentの境界 |
| 副作用テスト | 二重送信、重複登録、取消、ロールバック |
| 復旧テスト | タイムアウト、API停止、キュー停止、再開 |
| セキュリティテスト | Prompt Injection、データ漏えい、秘密情報露出 |
| 負荷テスト | 同時実行、キュー遅延、コスト上昇 |
| リストアテスト | バックアップからの復旧、系譜・監査ログ保持 |

### 評価データセット

評価は毎回同じ基準で比較できるように、匿名化した代表ケースを固定する。

```text
正常ケース
境界値ケース
欠損データ
古いデータ
重複データ
悪意ある入力
権限外データ
外部API障害
副作用が発生したケース
```

### 評価指標

- タスク成功率
- 必須項目の正確性
- 根拠の正確性
- 参照元の再現性
- 誤送信・二重実行件数
- 人間差し戻し率
- 承認漏れ件数
- 平均処理時間
- コスト / 1件
- 復旧成功率
- 不要な機密データ取得件数

単なるLLMの正答率ではなく、実際の業務結果と安全性を評価する。

### 提出候補の凍結

提出前に、次の構成を一つのRelease Manifestとして固定する。

```text
workflow_version
agent_versions
prompt_version
policy_version
connector_versions
model_version
evaluation_dataset_version
test_results
artifact_ids
approval_ids
known_limitations
rollback_plan
```

提出後に使用したAgent、プロンプト、ポリシー、コネクタを変更しない。変更する場合は新しいバージョンとして再評価する。

### 提出ゲート

```text
提出可能
  ├─ 必須テスト合格
  ├─ 評価基準達成
  ├─ 権限テスト合格
  ├─ 副作用テスト合格
  ├─ 監査ログ確認済み
  ├─ ロールバック手順あり
  ├─ 既知の制限を記載
  └─ 承認者が確定
```

一つでも重要項目が未達なら、`提出不可`または`条件付き提出`にする。条件付き提出では、対象会社、対象ユーザー、許可操作、期限、監視担当を明記する。

### 提出後のループ

本番公開は完了ではなく評価の開始とする。

```text
公開
  ↓
カナリア実行
  ↓
実績・エラー・差し戻しを収集
  ↓
SLOと評価指標を確認
  ↓
問題があれば停止・ロールバック
  ↓
評価データ、テストケース、Runbookを更新
  ↓
次のVersionを作成
```

### 成果物の提出状態

```text
IN_DEVELOPMENT
  → TESTING
  → EVALUATING
  → HUMAN_REVIEW
  → RELEASE_CANDIDATE
  → APPROVED
  → SUBMITTED
  → CANARY
  → PRODUCTION
  → MONITORED

各状態から
  → REJECTED
  → ROLLED_BACK
  → SUSPENDED
```

### 提出パッケージ

提出時は、成果物だけでなく次を一緒に保存する。

- 最終成果物
- 入力原本と参照根拠
- テスト結果
- 評価結果
- 承認記録
- 使用したAgent・Workflow・モデルのVersion
- 既知の制限
- 監視項目と通知先
- ロールバック手順
- 関連するRunとArtifactのID

これにより、提出後に「何を根拠に公開したか」を再現できる。
